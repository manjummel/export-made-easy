# Error Handling Strategy

## Structured Error Response

All errors returned by the API follow this envelope:

```json
{
  "error_code": "VALIDATION_ERROR",
  "message": "Human-readable description",
  "details": {},
  "request_id": "uuid-v4",
  "timestamp": "2026-08-12T12:00:00Z"
}
```

## Error Code Registry

| error_code | HTTP Status | Description |
|---|---|---|
| `VALIDATION_ERROR` | 422 | Request payload failed Pydantic validation |
| `AUTHENTICATION_ERROR` | 401 | Missing or invalid JWT token |
| `AUTHORIZATION_ERROR` | 403 | Valid token but insufficient permissions |
| `RESOURCE_NOT_FOUND` | 404 | Requested entity does not exist in scope |
| `DATABASE_ERROR` | 500 | SQLAlchemy persistence failure |
| `AI_SERVICE_ERROR` | 502 | AI engine returned an unexpected response |
| `RAG_SERVICE_ERROR` | 503 | Vector knowledge store is unavailable |
| `REQUEST_TIMEOUT` | 504 | Upstream AI/RAG call exceeded configured timeout |
| `WEBSOCKET_ERROR` | — | WebSocket handshake or streaming failure |
| `LOW_CONFIDENCE` | 422 | AI result confidence below acceptable threshold |
| `INSUFFICIENT_EVIDENCE` | 422 | Factual claim lacks required source citations |
| `INTERNAL_SERVER_ERROR` | 500 | Unhandled exception caught by global handler |
| `INSUFFICIENT_DATA` | 400/404 | Domain data is unavailable (e.g. unknown destination) |

## Error Handling Layers

### 1. Pydantic Schema Validation
- FastAPI raises `RequestValidationError` automatically for malformed payloads.
- Custom `@validator` on `PlanStep.evidence` blocks unsupported factual claims before any DB write.

### 2. Domain Exception Classes (`app/core/exceptions.py`)
All custom exceptions extend `HTTPException` and return standard structured responses:
- `AuthenticationError` (401)
- `AuthorizationError` (403)
- `ResourceNotFoundError` (404)
- `AIServiceError` (502)
- `RAGServiceError` (503)
- `RequestTimeoutError` (504)
- `LowConfidenceError` (422)
- `InsufficientEvidenceError` (422)
- `DatabaseError` (500)
- `WebSocketError` (non-HTTP, handled within WS handler)

### 3. Middleware Layer (`app/middleware/error_handler.py`)
`ErrorHandlerMiddleware` wraps every request, catches any uncaught exception, and formats it as a standard 500 envelope with `request_id` generated by `RequestIdMiddleware`.

### 4. WebSocket Error Handling (`app/api/v1/chat.py`)
- JSON decode errors send an inline `error` event over the socket.
- `asyncio.wait_for` with 5 s timeout prevents hanging on slow clients.
- `WebSocketDisconnect` is caught and logged cleanly.
- All errors trigger `trace_manager.complete_run()` with the error message.

## Request IDs
Every response includes `X-Request-ID` (header) and `request_id` (body).  
If the client supplies `X-Request-ID`, it is echoed back.  
All log lines are prefixed with `req_id=<uuid>` for full traceability.
